# Flounder: Java / SQL ranking experiment

## Статус пакета

Это исходники исследовательского стенда, подготовленные по присланному коду.
Сборка Maven, PostgreSQL-тесты и измерения автором пакета в этой среде НЕ запускались.
В архиве нет выдуманных результатов. Наличие исходников не подтверждает гипотезу.

## Быстрый запуск

Распакуйте архив ОТДЕЛЬНО от рабочего backend. Не копируйте schema.sql в production migrations.
Нужны Java 21, Maven и работающий Docker. Запускайте команды из каталога с pom.xml.

```bash
java -version
mvn -version
docker info
mvn -Dresearch.benchmark=false test
```

Если первый запуск завершился BUILD SUCCESS:

```bash
mvn -Dresearch.benchmark=true -Dresearch.batch=0 -Dresearch.samples=30 test
mvn -Dresearch.benchmark=true -Dresearch.batch=32 -Dresearch.samples=30 test
```

Второй профиль обязателен для интерпретации влияния JPA batching: нельзя показывать только
выигрыш SQL над заведомо не настроенным вариантом. Эти два значения — явно выбранные
экспериментальные настройки, НЕ извлечённые настройки вашего production.
Профиль 32 сам по себе не означает, что batching реально сработал: проверьте jdbc-metrics.csv.

При отсутствии установленного Maven можно использовать существующий mvnw из backend,
передав ему `-f` с путём к pom.xml этого отдельного проекта. Wrapper в архив не включён.
Доступ к Интернету нужен Maven/Docker для первого получения зависимостей и образа.

Дополнительные параметры:

```bash
mvn -Dresearch.benchmark=true -Dresearch.batch=32 -Dresearch.sizes=8,64,256 \
    -Dresearch.warmup=5 -Dresearch.samples=50 test
```

По умолчанию benchmark ВЫКЛЮЧЕН. Сначала должны пройти проверки.
Один JUnit-метод выполняет последовательность функциональных сценариев и только затем,
при включённом флаге, замеры. Это не следует представлять как сотни отдельных JUnit-тестов.
При функциональной ошибке измерения не начинаются. При ошибке посреди замеров полная
таблица замеров не публикуется. functional-checks.csv содержит только завершённые проверки;
полный исход ошибки находится в Surefire.

## Выходные артефакты

После запуска: target/research/batch-0/<run>/ или batch-32/<run>/.

- functional-checks.csv: успешно завершённые функциональные сценарии и проверка парсеров;
- status.txt: завершён ли функциональный прогон и выполнены ли измерения;
- raw-timings.csv: исходное время каждого вызова и порядок JAVA/SQL;
- summary.csv: медиана, квартиль 25/75, минимум и максимум, миллисекунды;
- jdbc-metrics.csv: отдельный инструментированный прогон JDBC;
- datasets.csv: воспроизводимые входные наборы;
- environment.properties: Java, ОС, PostgreSQL, batch_size, параметры и хеш набора.

Отчёт Surefire: target/surefire-reports/.
Передавайте результаты только из полностью завершённого запуска.

## Предмет и границы

Исследуется назначение мест ВНУТРИ ОДНОЙ competitionUnitId, ASC или DESC.
Это НЕ итоговые места по дисциплине и НЕ командный зачёт.
Оба варианта завершают транзакцию с записью статусов, мест, времени и версий.
Статусы PENDING/VALID ранжируются. ВСЕ остальные статусы неизменны, включая старое место.
Равные значения получают последовательные разные места. Дополнительный порядок — строковый
канонический UUID результата; SQL использует COLLATE "C". Это техническое правило эталона,
НЕ доказательство соответствия спортивному регламенту равных мест.

Размер 8 — небольшой контрольный набор, а не установленная вместимость вашего бассейна.
64 и 256 — исследовательские нагрузки; не объявляйте их обычным плавательным заплывом.
При необходимости замените research.sizes на реальные размеры единицы вашего MVP.
Выигрыш только на больших наборах не подтверждает ускорение на обычном маленьком заплыве.

## Отличия от присланного production

1. Три сущности повторяют присланные поля и JPA-отображения, но код форматирован заново,
   поэтому это не побайтовые копии оригиналов.
2. Интерфейсы репозиториев сокращены до нужных для стенда операций; это явно раскрыто,
   подсчёт LOC/методов не проводится.
3. Java-ветка сохраняет структуру существующего ранжирования: загрузка entries и результатов,
   проверка, очистка места, сортировка, установка места/статуса, saveAll.
4. Проверяются и PENDING, и VALID с плохим raw_value.
5. Добавлен детерминированный порядок равных значений.
6. Для обеих реализаций зафиксирован один УЗКИЙ текстовый числовой контракт (см. ниже).
7. Проверка существования/публикации и блокировки вынесены в общий транзакционный слой.
8. Оба варианта используют один момент updated_at, округлённый до микросекунд.
9. BusinessException заменён локальным RuleFailure с такими же исследуемыми кодами.
   Контроллеры, HTTP-статусы, тексты ошибок и GlobalExceptionHandler здесь не тестируются.
10. Зависимости и инфраструктура изолированы: нет Kafka/Redis/Security, нет запуска всего MVP.

Java-ветку следует подписывать «реализация на основе production после фиксации контракта»,
а НЕ «неизменённый production-код». Общий слой меняет исходный протокол конкурентного доступа;
его стоимость входит в оба измерения. Это сравнение двух реализаций с общими гарантиями,
а не измерение текущего публичного endpoint как есть.

## Числовой контракт стенда

- Десятичное число: [+-]?[0-9]+([.][0-9]+)?
- Время: [0-9]+:[0-9]{1,2}([.][0-9]+)?, секунды < 60.
- Минуты целые, десятичный разделитель — точка, нет пробелов.
- Нет экспонент, hexadecimal float, NaN, Infinity, суффиксов D/F.
- Максимальная длина 50, как у raw_value.
- Обычные отрицательные десятичные числа сохранены: исходный общий парсер их допускает.
  Это НЕ утверждение, что отрицательное время допустимо спортивным регламентом.
- -0 нормализуется к +0 для согласования Java Double.compare с SQL-сравнением.
- Числовая модель — double precision / Double, не вводим decimal только в один вариант.

Это намеренное изменение/уточнение исходного парсера, который допускал больше форматов.
Нельзя заявлять полную совместимость со всеми строками Double.parseDouble.
Паритет двух парсеров проверяется на детерминированном наборе; это не формальное доказательство
эквивалентности на всём пространстве входов. Контрольные ожидаемые места заданы вручную;
для нагрузочных наборов используется независимый расчёт по BigDecimal.

## Схема

Три исследуемые таблицы, колонки, индексы, FK и версии соответствуют присланному фрагменту.
Родительские event_disciplines и registrations — минимальные ID-only заглушки для FK.
Полный Flyway-набор продукта НЕ используется; неизвестные триггеры/политики/прочие связи не моделируются.
SQL-функция experiment_numeric существует только в отдельной контейнерной БД.
Hibernate проверяет отображения через ddl-auto=validate, а не создаёт таблицы.
Пользовательский SQL separator @@ нужен для PL/pgSQL-функции.

## Конкурентность

Обе ветки внутри одной транзакции блокируют:
1. строку competition_units (статус читается после получения блокировки);
2. существующие entries в порядке ID;
3. существующие results в порядке ID.

Блокировки строк предотвращают изменение уже заблокированных строк до завершения транзакции.
FK-зависимости также участвуют в блокировках. Все блокировки здесь намеренно общие для A/B.
В SQL version увеличивается явно; это НЕ выдаётся за автоматическое применение JPA @Version.
Конкурентные изменения сериализуются общим слоем, а не сравниваются по optimistic exception.

Проверяются два конкретных interleaving: публикация коммитится до получения unit-lock;
редактор держит result-lock, затем сохраняет новое значение, после чего пересчёт видит его.
Тест ждёт реальное блокирование в pg_stat_activity, а не опирается на один sleep.
Внедрение ошибки UPDATE проверяет откат всей операции.
Это не исчерпывающий concurrency-proof всех пользовательских сценариев и не тест
существующего use case публикации. Массовые изменения связей и вся политика публикации
полного продукта находятся вне стенда. Для встраивания нужен общий протокол всех writers.

## Методика времени и JDBC

- Замер снаружи Spring transactional proxy; commit включён.
- Создание/восстановление fixture и проверки результата исключены из времени.
- Каждый повтор начинает с одинаковых PENDING и version=0.
- JAVA/SQL и SQL/JAVA чередуются; прогрев выполняется отдельно.
- Каждый измеренный результат проверяется вне замеряемого интервала.
- JDBC-счётчики собираются ОТДЕЛЬНО; во временных прогонах выдаются необёрнутые connections.
- Метрика resultset_rows_consumed — число успешных ResultSet.next(), НЕ байты,
  НЕ строки, просмотренные PostgreSQL внутри запроса, и НЕ полная сетевая нагрузка.
- jdbc_executions — число вызовов execute*/executeBatch на JDBC, НЕ измеренные TCP-roundtrips.
- batch_items_submitted — число вызовов addBatch, не дополнительное число roundtrips.
- Один контейнер и одна JVM на запуск; 30 повторов дают предварительную оценку разброса.
- Для более устойчивого вывода повторите отдельные Maven-запуски и сохраните все результаты.
- SQL parsing выполняется PL/pgSQL-функцией, что может ограничить SQL-производительность.
  Это часть выбранной реализации, а не вывод о максимальной скорости PostgreSQL.

## Гипотеза и правило интерпретации

До первого прогона фиксируем:
«Для согласованного контракта пересчёта мест внутри одной стартовой единицы SQL-реализация
уменьшает число строк результатов, читаемых приложением, и время операции с сохранением
при совпадении мест, статусов, отказов и исследуемых конкурентных сценариев».

Корректность — обязательный допуск, а не допустимая жертва производительности.
Части гипотезы оцениваются раздельно. Выигрыш по ResultSet-строкам не доказывает ускорение.
Нельзя назвать меньший шумный median доказанным выигрышем; смотрите разброс и повторные запуски.
Если на малых размерах выигрыша нет, это полноценный результат, не причина менять пороги.
Не переименовывайте подтверждение корректности в подтверждение производительности.
Автоматического «гипотеза подтверждена» в инструменте нет.

## Что отправить для разбора

После успешных запусков обоих batch-профилей: последние законченные run-каталоги целиком
и текст BUILD SUCCESS / отчёт Surefire. При первой ошибке — полный первый блок ERROR
с причиной Caused by; не исправляйте настройки наугад и не отключайте проверки.
